# What Happens Next? 👀

You've opened your Pull Request.

So... what happens now?

Your contribution is now in the hands of the project maintainers.

They'll review your changes and decide what needs to happen next.

Don't worry if you're not sure what to expect. This is a normal part of open source.

---

## 1. Your Pull Request gets reviewed

A maintainer will look at your changes.

They might check things like:

* Does the change solve the problem?
* Is the information correct?
* Does it follow the project's guidelines?
* Is the formatting consistent?
* Does anything need to be changed?

For a simple contribution like adding your name, the review may be very quick.

For a larger contribution, the discussion may take longer.

---

## 2. You may get feedback

A maintainer might ask you to change something.

For example:

> "Could you use your GitHub username instead of your display name?"

Or:

> "Could you fix the formatting on this line?"

This is called **requested changes**.

Don't worry.

It doesn't mean your contribution was bad.

It means someone is helping you improve it.

---

## 3. Make the requested changes

If a maintainer asks you to make a change, go back to your local project.

Make the change on the **same branch** you used for your Pull Request.

For example:

```text id="2s5f9g"
add-my-name
```

After making the change:

```bash id="o4h1f4"
git add .
```

Then commit it:

```bash id="k9u6gc"
git commit -m "Update contributor entry"
```

Then push it:

```bash id="h0szqv"
git push
```

You don't need to create another Pull Request.

Your existing Pull Request will automatically update with the new commit.

---

## 4. The maintainer may approve your Pull Request

If everything looks good, the maintainer may approve your changes.

You might see something like:

```text id="5ov8rd"
Approved
```

That means the reviewer is happy with the changes.

But approval and merging are two different things.

---

## 5. Your Pull Request gets merged

Once the maintainers are ready, they can merge your Pull Request.

When that happens, your changes become part of the main CNI project.

The journey looks like:

```text id="50l6ev"
Your branch
     ↓
Pull Request
     ↓
Review
     ↓
Feedback
     ↓
Changes
     ↓
Approval
     ↓
Merge 🎉
     ↓
CNI project
```

---

# What if it takes a while?

Don't panic if your Pull Request isn't reviewed immediately.

Open-source projects are usually maintained by people who have other responsibilities too.

Maintainers may be:

* Working full-time
* Studying
* Running a business
* Managing a community
* Working on other parts of the project
* Dealing with personal responsibilities

Give people some time.

If the project has contribution guidelines about when and how to follow up, follow those guidelines.

---

# What if nobody responds?

If you've waited for a reasonable amount of time, you can politely follow up.

For example:

> Hi! Just checking in on this Pull Request when you get a chance. Thanks!

Keep it friendly.

Avoid repeatedly commenting or demanding that someone review your contribution.

Remember: open source is a community.

---

# What if your Pull Request is closed?

A Pull Request can be closed without being merged.

That can happen for many reasons.

For example:

* The issue has already been solved
* The change isn't needed
* The project decided to take a different approach
* The contribution needs to be redesigned
* The Pull Request is no longer relevant

A closed Pull Request doesn't mean:

> "You're not good enough for open source."

It simply means that particular contribution wasn't merged.

You can learn from the discussion and try again.

---

# What if your contribution gets merged?

🎉 Congratulations!

You've made your first contribution to an open-source project.

You can now say:

> "I've contributed to an open-source project."

But more importantly, you now understand the basic workflow.

```text id="ygs6lw"
Find a project
      ↓
Fork
      ↓
Clone
      ↓
Branch
      ↓
Make a change
      ↓
Commit
      ↓
Push
      ↓
Pull Request
      ↓
Review
      ↓
Merge
```

This same workflow can be used for much bigger contributions.

---

# Your first contribution doesn't have to be your best contribution

Your first contribution might be:

* Adding your name
* Fixing a typo
* Improving a sentence
* Updating documentation
* Fixing a broken link
* Adding an example
* Translating something
* Reporting a bug

That's okay.

The goal of your first contribution isn't to prove that you're an expert.

The goal is to **learn how contributing works**.

Your next contribution can be bigger.

---

# You now know more than you did before

Think about where you started.

Maybe you didn't know:

* What open source was
* What GitHub was
* What a repository was
* What a fork was
* What a branch was
* What a commit was
* What a Pull Request was

Now you understand the basic workflow.

That's progress.

One contribution can become two.

Over time, you may find projects that match your interests and skills.

You might discover that you enjoy:

* Designing interfaces
* Fixing bugs
* Building features
* Translating projects

Explore.
